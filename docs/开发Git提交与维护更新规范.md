# 开发、Git 提交与维护更新规范

## 1. 目的与适用范围

本文档规定项目从需求进入、分支开发、提交、合并、发布到后续维护的基本流程，适用于源代码、测试、脚本、CI、配置、README（书写与审核见第 10 章）、规格、变更记录和 Skill 文档变更。

项目已有的 `CONTRIBUTING.md`、发布流程和验证脚本优先于本文档中的默认值。

## 2. 基本原则

1. 每个变更先明确目标、范围和验收条件，再开始修改。
2. 一个提交只表达一个完整、可验证、可回滚的意图。
3. 提交信息必须说明改了什么、为什么改、如何验证。
4. 代码、测试、文档和变更记录保持同步。
5. 版本号只在发布阶段更新，日常开发提交不提前写入版本号。
6. 未验证的结论、未复现的问题和已知风险必须明确记录。
7. 不直接在稳定分支开发，不通过改写历史隐藏错误提交。

## 3. 开发前检查

开始工作前确认当前仓库、目标分支、任务范围和验收条件正确，并检查是否涉及公共 API、数据格式、依赖、CI、版本号或发布说明。

```powershell
git status --short
git branch --show-current
git log -5 --oneline
git fetch origin
```

## 4. 分支规范

从最新稳定分支创建短期工作分支：

```powershell
git switch master
git pull --ff-only origin master
git switch -c feature/<short-name>
```

| 前缀 | 用途 |
|---|---|
| `feature/` | 新功能或能力扩展 |
| `fix/` | 缺陷修复 |
| `refactor/` | 不改变外部行为的重构 |
| `docs/` | 文档和规格维护 |
| `test/` | 测试和验证工具 |
| `chore/` | 依赖、构建、CI 和工程维护 |
| `hotfix/` | 线上紧急修复 |

分支名使用短英文或 kebab-case，不绑定版本号。版本边界由发布提交和 Git 标签表达。

## 5. 提交信息规范

### 5.1 标题

日常提交使用 Conventional Commits：

```text
<type>(<scope>): <简短变更说明>
```

允许的类型：

| type | 使用场景 |
|---|---|
| `feat` | 新增能力 |
| `fix` | 修复缺陷或错误边界 |
| `docs` | 文档、规格和变更记录 |
| `test` | 测试和验证逻辑 |
| `refactor` | 不改变外部行为的重构 |
| `chore` | 依赖、构建、CI 和工具维护 |

`scope` 使用具体模块或责任域，例如 `core`、`gates`、`evidence`、`cli`、`platforms`、`ci`。

示例：

```text
feat(evidence): 增加证据完整性校验
fix(cli): 修复配置加载时的参数解析
test(gates): 覆盖禁用 profile 的边界路径
refactor(platforms): 拆分平台配置与参数注入模块
docs(process): 更新发布和回滚流程
```

### 5.2 正文

涉及逻辑、协议、兼容性或发布影响的提交必须包含正文：

```text
影响范围：
- <模块、入口或用户场景>

关键决策：
- <为何采用当前实现>
- <兼容性或边界处理>

验证：
- <完整命令>
- <结果>

风险与后续：
- <已知限制或后续任务>
```

提交正文应记录事实，不以“已测试”“应该没问题”等模糊表述代替实际结果。

### 5.3 提交粒度

推荐按“规格或测试准备 → 实现变更 → 文档和变更记录同步 → 发布聚合提交”拆分。不要把格式化、无关重构、版本升级和功能实现混在一个日常提交中。

## 6. 开发与验证

- 修复缺陷：先增加能复现问题的测试，再修复实现；
- 新功能：覆盖正常路径、边界条件和错误路径；
- 重构：先确认现有测试基线，再执行重构和回归；
- 文档或配置：执行链接、格式、配置加载或对应验证脚本。

提交前至少执行：

```powershell
python -m pytest -q
ruff check goalanchor tests scripts
git diff --check
```

按变更范围追加类型检查、构建、打包、端到端、压力测试或多平台验证，并在提交正文记录实际命令和结果。

Ruff 检查范围与 CI 保持一致，仅覆盖自有 Python 代码；上游 Skill 快照不纳入该门禁，不以修改上游文件来消除快照诊断。

## 7. Pull Request 与合并

PR 描述至少包括：变更目标、影响范围、主要决策、测试结果、兼容性或迁移影响、已知风险、后续工作，以及关联任务或规格。

合并前确认 CI 和审查通过，提交历史清晰，目标分支已同步，没有秘密、构建产物、临时文件或机器专属绝对路径。合并后删除已完成的短期分支。

## 8. 固定提交架构

项目提交历史必须保持“工作提交 → 分支合并提交 → 发布聚合提交 → 版本标签”的层次结构。该结构是项目的长期维护约束，不能随意改成无法区分来源的扁平历史。

标准拓扑如下：

```text
feature/<name> 或 fix/<name>
        │
        └── <type>(<scope>): <具体实现提交>
                         │
                         ▼
master ──────── 合并提交：合并 feature/<name> 或 fix/<name>
                         │
                         ▼
                 vX.Y.Z 发布聚合提交
                         │
                         ▼
                     tag vX.Y.Z
```

具体要求：

1. 功能或修复先在独立分支完成，分支内的实现提交保留清晰的 `type(scope)` 标题；
2. 通过 PR 合并到 `master` 时保留一个明确的合并提交，提交说明写明被合并的分支和变更主题；
3. 发布时在 `master` 上创建单独的 `vX.Y.Z <发布说明>` 聚合提交；
4. 发布聚合提交只负责版本号、CHANGELOG、README、贡献规范和发布资料同步，不承载未审查的大规模功能实现；
5. 发布聚合提交之后创建同名 annotated tag，标签必须直接指向该发布提交；
6. 多个相关功能可以分别合并到 `master`，但发布提交必须位于这些合并提交之后；
7. 不使用 squash、rebase 或手工改写破坏已经发布的提交拓扑；如果项目明确要求保留合并节点，PR 合并必须使用保留合并提交的方式；
8. 已发布的提交、合并节点和标签不移动、不复用、不删除。

标准示例：

```text
<feature/fix 分支>  fix(platforms): 完成具体修复
                         │
                         └── master 合并：合并 fix/platforms
                                      │
                                      └── v0.5.1 发布审核链修复
                                                   │
                                                   └── tag v0.5.1
```

检查提交架构：

```powershell
git log --graph --oneline --decorate --all
git show --summary <merge-commit>
git show <release-commit> --stat
git describe --tags --exact-match <release-commit>
```

提交或发布前发现拓扑不符合本节要求时，应暂停合并，先修正分支和合并方式，再继续发布流程。

## 9. 版本发布与维护更新

项目采用 SemVer：`MAJOR` 表示破坏性变更，`MINOR` 表示兼容的新能力，`PATCH` 表示兼容性修复。

### 9.1 Release 命名

- Git tag 与 Release 标题均为纯 `vX.Y.Z`，不使用主题后缀或任何修饰语（与 v0.7.0 及之前所有版本保持一致）。
- 版本主题、亮点与说明一律写入 Release 说明正文和 `CHANGELOG.md`，不进入标题。

发布步骤：

1. 确认目标版本和变更范围；
2. 更新运行时版本单一来源；
3. 将 `CHANGELOG.md` 的未发布内容定版；
4. 同步 README、贡献规范、规格和示例中的版本引用；
5. 执行完整测试、质量门禁和打包检查；
6. 在稳定分支创建发布聚合提交：

   ```text
   vX.Y.Z <发布说明>
   ```

7. 创建 annotated tag 并推送提交和标签：

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z <发布说明>"
   git push origin master --follow-tags
   ```

已发布标签不可移动、不可复用。维护更新应说明是否改变行为、是否需要迁移和应使用的版本号。

## 10. README 书写与审核规范

### 10.1 适用范围与分层

本章适用于仓库根 `README.md` 与 `README.en.md`。README 是项目的第一入口：新读者据它判断项目是什么、能不能用、怎么开始；它必须反映当前已发布状态，而不是开发计划或变更历史。

README 分两层，职责不混用：

| 层 | 文件 | 职责 |
|---|---|---|
| 产品 README | 仓库根 `README.md` / `README.en.md` | 项目定位、安装、使用、配置、支持范围、版本与兼容性 |
| 工作区/入口 README | 仓库外工作区根（如适用） | 只做目录导航与入口链接，不重复产品说明 |

### 10.2 标准章节结构

产品 README 按以下顺序组织。标注“必选”的章节不得缺失；“按需”章节在内容量达到时补充，补充后必须进入目录。

| 顺序 | 章节 | 必选 | 内容要求 |
|---|---|---|---|
| 1 | 标题与徽章 | 必选 | 项目名；徽章指向真实存在的 URL（版本、许可证、CI） |
| 2 | 语言切换 | 必选 | `README.md` 与 `README.en.md` 顶部互链 |
| 3 | 目录 | 必选 | 列出全部 `##` 章节，锚点有效 |
| 4 | 项目简介 | 必选 | 项目是什么、解决什么问题、不替代什么（边界声明） |
| 5 | 主要功能 | 必选 | 按能力分组，与实际模块对应 |
| 6 | 当前版本 | 必选 | 只列**最新版本**：版本号、日期、Release 链接、验收状态；不罗列历史版本 |
| 7 | 运行环境 | 必选 | 语言版本、操作系统、外部依赖（Agent CLI、Node 等） |
| 8 | 安装与运行 | 必选 | 全部安装路径（源码、wheel、Skill、插件）+ 快速运行示例 |
| 9 | 使用说明 | 必选 | 基本流程、API 示例、命令请求/输出字段 |
| 10 | 配置 | 必选 | 配置方式分类表；字段级 schema 用表格；性能与规模上限 |
| 11 | 项目结构 | 必选 | 目录树与实际顶层一致；注明本地生成物 |
| 12 | 依赖与开发 | 必选 | 运行时依赖、开发依赖、本地质量检查命令 |
| 13 | 核心术语 | 按需 | 领域专有概念集中解释，注明对应源码 |
| 14 | 支持的应用/平台 | 按需 | 按接入形态分组，逐项说明用途、接入方式、角色、支持级别 |
| 15 | 版本与兼容性 | 按需 | SemVer、已知限制、升级与回滚、支持周期 |
| 16 | 贡献指南 | 必选 | 简要流程 + 指向 `CONTRIBUTING.md` |
| 17 | 安全 | 必选 | 漏洞报告渠道 + 指向 `SECURITY.md`；有信任边界时说明 |
| 18 | 许可证 | 必选 | 本项目许可证与第三方范围界定 |
| 19 | 更多资料 | 按需 | 规格指南、示例、相关文档链接 |

### 10.3 内容准确性要求

1. **单一事实源**：版本号以运行时版本定义（`goalanchor/_version.py`）为准；CLI 子命令与参数以 `--help` 实测为准；配置字段与默认值以配置类源码为准（如 `platforms/platform_config.py`）；不凭记忆或旧文档转写。
2. **命令可执行**：README 中每条 shell 命令必须与当前 CLI 一致，快速运行一节的示例必须实跑通过；会产生模型用量或网络请求的命令必须显式注明。
3. **安装与升级路径实测**：写入 README 前必须验证可行。典型错误是把“从 Releases 下载 wheel”写成 `pip install <包名>`——包未发布到 PyPI 时该命令必然失败，必须在文档中注明。
4. **示例与签名一致**：API 示例的参数名、位置/关键字参数与当前签名一致；请求/输出字段表与序列化 schema 一致。
5. **只描述最新状态**：不写“新版本新增了什么”式的更新说明，不罗列历史版本；历史归 `CHANGELOG.md`。
6. **边界明确**：说明工具不能替代什么（真实测试、外部事实核验、工程判断）、哪些字段不可核验、哪些功能仍返回未实现状态。
7. **数字有来源**：模块数、用例数、文件数、通过率等统计数字必须能在源码、测试或验收映射中复现，写明统计时点或来源。

### 10.4 格式与排版

- 中文正文使用全角标点；代码、命令、标识符、文件路径一律用反引号包裹，其内部保持半角符号。
- 字段级说明用表格，推荐“字段 | 必填 | 说明”或“项 | 默认值 | 说明”三列；避免用长段落罗列字段。
- 相对链接必须可解析；内部锚点按 GitHub slug 规则生成（英文小写连字，中文标题保留汉字、空格转连字符）。
- 目录、章节标题、锚点三者同步；增删章节后立即更新目录。
- `README.md` 与 `README.en.md` 章节结构和表格内容对齐，仅语言不同。
- 行尾风格与仓库现有文件保持一致，禁止在同一次提交中混合行尾；批量生成或脚本修改 Markdown 时必须显式指定换行符（Windows 下 `write_text` 会默认写入 CRLF）。
- 徽章、外链指向真实 URL；不引用内网地址或机器专属绝对路径。

### 10.5 审核检查清单

README 变更合入前逐项核对：

- [ ] 所有 shell 命令与 CLI `--help` 输出一致
- [ ] 快速运行示例实跑通过（或注明所需外部条件）
- [ ] API 示例与当前函数签名一致
- [ ] 默认值（超时、并发、轮次等）与源码配置类一致
- [ ] 安装与升级路径已实测；未发布到 PyPI 时不得出现 `pip install <包名>`
- [ ] 项目结构树与实际顶层文件一致，生成物已注明
- [ ] 版本号、发布日期、Release 链接与运行时版本和 Releases 页面一致
- [ ] 相对链接 0 缺失；目录锚点全部有效
- [ ] 中英文版章节结构与表格内容对齐
- [ ] 只保留最新版本信息，无历史版本罗列与“新增功能”式表述
- [ ] 中文正文全角标点，代码元素反引号包裹
- [ ] 无秘密、个人数据、机器专属绝对路径
- [ ] 行尾一致，`git diff --check` 通过
- [ ] 统计数字有可复现来源

### 10.6 变更时机

以下变更必须在同一任务或紧随其后的文档任务中同步 README（与第 9 章发布步骤第 4 条衔接）：

- 版本发布：版本表、徽章、升级与兼容性说明；
- CLI 子命令或参数变化：命令列表、快速运行、审核请求/输出字段；
- 配置 schema 或默认值变化：配置章节与性能上限表；
- 新增或移除顶层文件/目录：项目结构树；
- 支持的应用、安装目标或平台调度能力变化：支持的应用章节；
- 依赖项或 Python 版本要求变化：运行环境与依赖章节。

README 与实际行为不一致时，以代码为准修正 README；若 README 描述的是期望行为，则必须先改代码和测试，再更新文档。

## 11. 变更记录

涉及代码、测试、配置、发布或质量门禁的任务，应记录：任务 ID 和状态、目标与验收标准、Gate 或审核关联、改动文件、实现摘要、测试命令和结果、回归结果、剩余风险、提交和工作树状态。

如果目标、验收条件、核心假设或交付范围变化，应先更新规格或重新进入计划审核，再继续实现。

## 12. 回滚与紧急修复

- 未发布提交：使用反向提交或修复提交恢复；
- 已合并功能：创建 `revert/<short-name>` 分支并通过 PR 合并；
- 已发布版本：发布新的补丁版本，不移动旧标签；
- 线上紧急问题：从受影响的稳定标签或稳定分支创建 `hotfix/`，完成最小修复和专项验证后合并。

回滚记录应说明原因、影响范围、恢复版本、验证结果和后续修复计划。

## 13. 边界

### 始终执行

- 使用正确的工作分支；
- 保持提交单一、可读、可回滚；
- 为行为变更补充或更新测试；
- 提交前运行项目规定的验证；
- 同步必要的文档、版本和任务记录；
- 记录已知风险和未覆盖场景。

### 需要先评估并记录

- 公共 API、协议、数据格式或持久化结构变化；
- 新增生产依赖；
- CI、发布权限或部署配置变化；
- 安全、隐私、认证和授权逻辑变化；
- 破坏性重构和版本策略变化。

### 禁止

- 提交密钥、令牌、个人凭据或生产数据；
- 直接在稳定分支开发；
- 删除失败测试来制造通过结果；
- 移动或复用已发布标签；
- 未确认就用强制推送覆盖他人工作；
- 提交构建产物、临时缓存或机器专属绝对路径；
- 没有验证结果就宣称任务完成。

## 14. 提交前检查清单

- [ ] 当前分支和目标仓库正确
- [ ] 工作树没有无关修改
- [ ] 任务目标和验收条件明确
- [ ] 提交类型和 scope 正确
- [ ] 每个提交只有一个主要意图
- [ ] 正文包含影响范围、决策和验证
- [ ] 测试、质量检查和专项验证已执行
- [ ] 文档、CHANGELOG、版本引用已同步
- [ ] 没有秘密、临时文件或构建产物
- [ ] 任务记录包含结果、风险和提交信息
- [ ] `git diff --check` 通过
- [ ] PR 描述已说明兼容性和后续工作

## 15. AI/Codex 协作开发与提交操作

使用 AI 或 Codex 参与开发时，必须让每一步都可以由开发者复核。AI 负责分析、修改和验证，开发者保留对范围、结果和远端状态的最终控制权。

### 15.1 开发方式

推荐按以下顺序执行：

1. **读取上下文**：确认仓库根目录、项目文档、贡献规范、相关模块、测试入口和当前 Git 状态；
2. **确认范围**：说明目标、涉及文件、预期行为、验收条件和潜在风险；
3. **先查后改**：使用搜索、调用关系、历史提交和现有测试理解当前实现，不凭文件名猜测结构；
4. **小步修改**：只修改任务需要的文件，优先使用可审查的补丁方式，保留用户已有的未提交改动；
5. **同步测试**：行为变更同时更新测试，缺陷修复优先增加复现测试；
6. **运行验证**：先运行针对性测试，再运行项目规定的全量测试、质量检查和专项门禁；
7. **复核差异**：检查 `git diff`、`git diff --check`、文件清单和工作树，确认没有临时文件、秘密、无关格式化或机器专属路径；
8. **汇报结果**：说明完成内容、验证命令、结果、剩余风险和未执行的检查。

AI 不应在没有读取相关文档和代码的情况下直接改动；不能把猜测写成事实；遇到需求范围变化时应先更新任务目标或规格。

### 15.2 AI 的文件操作边界

- 读取、搜索、测试和查看 Git 历史属于常规分析操作；
- 修改应限制在用户任务范围内，并优先采用可恢复、可审查的补丁；
- 不覆盖用户已有的未提交修改；
- 不删除大量文件，不执行不可逆清理，不使用强制推送覆盖远端历史；
- 涉及凭据、生产数据、外部系统消息或权限变化时，必须停止并说明需要的人工决策；
- 生成的代码、文档和提交说明都必须以实际文件和命令结果为依据。

### 15.3 AI 的提交操作

AI 在提交前按以下顺序操作：

```powershell
git status --short
git diff --stat
git diff --check
git diff
```

确认差异只包含本次任务后，再明确添加目标文件：

```powershell
git add -- <文件路径>
git commit -m "<type>(<scope>): <简短变更说明>"
```

提交后立即检查：

```powershell
git status --short
git log -1 --oneline --decorate
```

提交正文应包含实际影响和验证结果。AI 不应为了让提交通过而跳过测试、删除测试、修改无关文件或伪造验证结果。

### 15.4 AI 的推送操作

只有在用户明确要求推送，或当前任务已经明确授权推送时，AI 才执行远端写操作。推送前确认：

- 当前分支和远端正确；
- 提交已经创建并且内容已复核；
- 工作树状态符合预期；
- 推送不会覆盖他人提交；
- 已完成要求的测试和质量检查。

推荐使用：

```powershell
git remote -v
git branch --show-current
git fetch origin
git push origin <branch>
```

推送后检查本地和远端指向同一个提交，并向开发者报告提交哈希、分支、远端和工作树状态：

```powershell
git status --short
git log -1 --oneline --decorate
git ls-remote --heads origin <branch>
```

AI 不执行未经授权的强制推送、标签移动、历史重写或远端删除。发布标签推送必须同时确认版本、CHANGELOG、发布提交和标签指向一致。

### 15.5 推荐的 AI 交付报告

```text
完成：<变更摘要>
文件：<实际修改文件>
验证：<命令及结果>
提交：<commit hash> <commit title>
推送：<remote>/<branch>，远端已确认
状态：工作树干净 / 仍有指定未提交文件
风险：<剩余风险或未执行检查>
```

## 16. GoalAnchor 落地说明

GoalAnchor 当前的仓库级细则以以下文件为准：

- `CONTRIBUTING.md`：分支、提交标题、版本和发布规则；
- `CHANGELOG.md`：版本变更记录；
- `pyproject.toml`：测试、ruff、mypy 和打包配置；
- `docs/`：仓库内随版本管理的开发者文档；
- 仓库外 `Doc/`：设计、任务交接和验证证据中心。

如果本文档与这些文件存在差异，应先修正规范来源，再执行受影响的开发或发布流程。
