# 开发、Git 提交与维护更新规范

## 1. 目的与适用范围

本文档规定项目从需求进入、分支开发、提交、合并、发布到后续维护的基本流程，适用于源代码、测试、脚本、CI、配置、README、规格、变更记录和 Skill 文档变更。

项目已有的 `CONTRIBUTING.md`、发布流程和验证脚本优先于本文档中的默认值。

## 2. 基本原则

1. 每个变更先明确目标、范围和验收条件，再开始修改。
2. 一个提交只表达一个完整、可验证、可回滚的意图。
3. 提交信息必须说明改了什么、为什么改、如何验证。
4. 代码、测试、文档和变更记录保持同步。
5. 版本号只在发布阶段更新，日常开发提交不提前写入版本号。
6. 未验证的结论、未复现的问题和已知风险必须明确记录。
7. 不直接在稳定分支开发，不通过改写历史隐藏错误提交。

## 3. 开发前检查

开始工作前确认当前仓库、目标分支、任务范围和验收条件正确，并检查是否涉及公共 API、数据格式、依赖、CI、版本号或发布说明。

```powershell
git status --short
git branch --show-current
git log -5 --oneline
git fetch origin
```

## 4. 分支规范

从最新稳定分支创建短期工作分支：

```powershell
git switch master
git pull --ff-only origin master
git switch -c feature/<short-name>
```

| 前缀 | 用途 |
|---|---|
| `feature/` | 新功能或能力扩展 |
| `fix/` | 缺陷修复 |
| `refactor/` | 不改变外部行为的重构 |
| `docs/` | 文档和规格维护 |
| `test/` | 测试和验证工具 |
| `chore/` | 依赖、构建、CI 和工程维护 |
| `hotfix/` | 线上紧急修复 |

分支名使用短英文或 kebab-case，不绑定版本号。版本边界由发布提交和 Git 标签表达。

## 5. 提交信息规范

### 5.1 标题

日常提交使用 Conventional Commits：

```text
<type>(<scope>): <简短变更说明>
```

允许的类型：

| type | 使用场景 |
|---|---|
| `feat` | 新增能力 |
| `fix` | 修复缺陷或错误边界 |
| `docs` | 文档、规格和变更记录 |
| `test` | 测试和验证逻辑 |
| `refactor` | 不改变外部行为的重构 |
| `chore` | 依赖、构建、CI 和工具维护 |

`scope` 使用具体模块或责任域，例如 `core`、`gates`、`evidence`、`cli`、`platforms`、`ci`。

示例：

```text
feat(evidence): 增加证据完整性校验
fix(cli): 修复配置加载时的参数解析
test(gates): 覆盖禁用 profile 的边界路径
refactor(platforms): 拆分平台配置与参数注入模块
docs(process): 更新发布和回滚流程
```

### 5.2 正文

涉及逻辑、协议、兼容性或发布影响的提交必须包含正文：

```text
影响范围：
- <模块、入口或用户场景>

关键决策：
- <为何采用当前实现>
- <兼容性或边界处理>

验证：
- <完整命令>
- <结果>

风险与后续：
- <已知限制或后续任务>
```

提交正文应记录事实，不以“已测试”“应该没问题”等模糊表述代替实际结果。

### 5.3 提交粒度

推荐按“规格或测试准备 → 实现变更 → 文档和变更记录同步 → 发布聚合提交”拆分。不要把格式化、无关重构、版本升级和功能实现混在一个日常提交中。

## 6. 开发与验证

- 修复缺陷：先增加能复现问题的测试，再修复实现；
- 新功能：覆盖正常路径、边界条件和错误路径；
- 重构：先确认现有测试基线，再执行重构和回归；
- 文档或配置：执行链接、格式、配置加载或对应验证脚本。

提交前至少执行：

```powershell
python -m pytest -q
ruff check .
git diff --check
```

按变更范围追加类型检查、构建、打包、端到端、压力测试或多平台验证，并在提交正文记录实际命令和结果。

## 7. Pull Request 与合并

PR 描述至少包括：变更目标、影响范围、主要决策、测试结果、兼容性或迁移影响、已知风险、后续工作，以及关联任务或规格。

合并前确认 CI 和审查通过，提交历史清晰，目标分支已同步，没有秘密、构建产物、临时文件或机器专属绝对路径。合并后删除已完成的短期分支。

## 8. 版本发布与维护更新

项目采用 SemVer：`MAJOR` 表示破坏性变更，`MINOR` 表示兼容的新能力，`PATCH` 表示兼容性修复。

发布步骤：

1. 确认目标版本和变更范围；
2. 更新运行时版本单一来源；
3. 将 `CHANGELOG.md` 的未发布内容定版；
4. 同步 README、贡献规范、规格和示例中的版本引用；
5. 执行完整测试、质量门禁和打包检查；
6. 在稳定分支创建发布聚合提交：

   ```text
   vX.Y.Z <发布说明>
   ```

7. 创建 annotated tag 并推送提交和标签：

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z <发布说明>"
   git push origin master --follow-tags
   ```

已发布标签不可移动、不可复用。维护更新应说明是否改变行为、是否需要迁移和应使用的版本号。

## 9. 变更记录

涉及代码、测试、配置、发布或质量门禁的任务，应记录：任务 ID 和状态、目标与验收标准、Gate 或审核关联、改动文件、实现摘要、测试命令和结果、回归结果、剩余风险、提交和工作树状态。

如果目标、验收条件、核心假设或交付范围变化，应先更新规格或重新进入计划审核，再继续实现。

## 10. 回滚与紧急修复

- 未发布提交：使用反向提交或修复提交恢复；
- 已合并功能：创建 `revert/<short-name>` 分支并通过 PR 合并；
- 已发布版本：发布新的补丁版本，不移动旧标签；
- 线上紧急问题：从受影响的稳定标签或稳定分支创建 `hotfix/`，完成最小修复和专项验证后合并。

回滚记录应说明原因、影响范围、恢复版本、验证结果和后续修复计划。

## 11. 边界

### 始终执行

- 使用正确的工作分支；
- 保持提交单一、可读、可回滚；
- 为行为变更补充或更新测试；
- 提交前运行项目规定的验证；
- 同步必要的文档、版本和任务记录；
- 记录已知风险和未覆盖场景。

### 需要先评估并记录

- 公共 API、协议、数据格式或持久化结构变化；
- 新增生产依赖；
- CI、发布权限或部署配置变化；
- 安全、隐私、认证和授权逻辑变化；
- 破坏性重构和版本策略变化。

### 禁止

- 提交密钥、令牌、个人凭据或生产数据；
- 直接在稳定分支开发；
- 删除失败测试来制造通过结果；
- 移动或复用已发布标签；
- 未确认就用强制推送覆盖他人工作；
- 提交构建产物、临时缓存或机器专属绝对路径；
- 没有验证结果就宣称任务完成。

## 12. 提交前检查清单

- [ ] 当前分支和目标仓库正确
- [ ] 工作树没有无关修改
- [ ] 任务目标和验收条件明确
- [ ] 提交类型和 scope 正确
- [ ] 每个提交只有一个主要意图
- [ ] 正文包含影响范围、决策和验证
- [ ] 测试、质量检查和专项验证已执行
- [ ] 文档、CHANGELOG、版本引用已同步
- [ ] 没有秘密、临时文件或构建产物
- [ ] 任务记录包含结果、风险和提交信息
- [ ] `git diff --check` 通过
- [ ] PR 描述已说明兼容性和后续工作

## 13. GoalAnchor 落地说明

GoalAnchor 当前的仓库级细则以以下文件为准：

- `CONTRIBUTING.md`：分支、提交标题、版本和发布规则；
- `CHANGELOG.md`：版本变更记录；
- `pyproject.toml`：测试、ruff、mypy 和打包配置；
- `docs/`：仓库内随版本管理的开发者文档；
- 仓库外 `Doc/`：设计、任务交接和验证证据中心。

如果本文档与这些文件存在差异，应先修正规范来源，再执行受影响的开发或发布流程。
